# Rendering benchmark analyzer

This standalone Python package analyzes completed R1 rendered-battle runs. It reads captured evidence and emits JSON; it does not launch the game or alter run data.

## Files and runtime

The package contains exactly three files:

- `analyze_r1.py` parses per-run evidence and compares replicate groups.
- `test_analyze_r1.py` contains synthetic parser and comparison checks.
- `README.md` documents usage, evidence requirements, and interpretation limits.

The analyzer and tests use only the Python standard library. Use CPython 3.12 for the documented workflow. The original 70-test run recorded CPython 3.12, but its exact patch version was not recorded. No third-party packages, game build tools, or GPU tools are needed to run the parser tests.

## Usage

From the repository root, substitute local paths for the uppercase placeholders:

```powershell
python tools/rendering-benchmark/analyze_r1.py analyze RUN_DIRECTORY
python tools/rendering-benchmark/analyze_r1.py compare --baseline BASELINE_A BASELINE_B --candidate CANDIDATE_A CANDIDATE_B
```

Each comparison group requires at least two distinct run directories. To run the synthetic suite, change into `tools/rendering-benchmark` and run:

```powershell
python -m unittest -v test_analyze_r1.py
```

The synthetic tests check parser behavior and do not measure game performance. They create disposable fixtures in Python's default temporary directory. To choose another location, set TEMP, TMP and TMPDIR for the test process to the same writable directory and verify the resolved tempfile location before running the suite.

## Evidence and qualification

A run requires the controller's `ready.json` and normal `exit.json`, one published `profile/RenderedBattleDiagnostic-*.txt`, one published `present/present-frame-timing-*.csv`, and `window-observations.json`. The analyzer checks process and executable hashes, ready/exit identities, source snapshot, Present owner and footer counts, the legacy 512-unit roster or one enumerated R2 profile, fixed seed/map/camera, and the exact 150-frame warmup plus 450-frame measured QPC phase. BEGIN and START must both report the literal seed `637808953`, matching the single canonical decimal seed immediately after `-runRenderedBattleBenchmark` in ready.arguments. Duplicate fixture options, a seed elsewhere in the arguments, and malformed seed text reject. BEGIN must identify `Fortress_Avalanche`; START must identify that fixture label or the native relative path `Maps\Fortress Avalanche\Fortress Avalanche.map` (slash direction and path case may normalize). Other leaves, directories, absolute paths, or map mismatches reject, even when all replicates share the same wrong seed/map. The eight slots must also use the native America/China/GLA/America sequence repeated, each with the exact emitted four-template mix and counts `8,8,24,24`: AmericaTankCrusader, AmericaVehicleHumvee, AmericaInfantryRanger, AmericaInfantryMissileDefender; ChinaTankBattleMaster, ChinaTankGattling, ChinaInfantryRedguard, ChinaInfantryTankHunter; or GLATankScorpion, GLAVehicleTechnical, GLAInfantryRebel, GLAInfantryTunnelDefender. Different names, counts, order, or faction mixes reject even if every replicate agrees. Object IDs retain the existing uniqueness check and are excluded from template-mix comparison. Integer receipt values must be JSON integers (booleans and all JSON floats, including integral-looking `0.0`, are rejected); game and launcher PID/parent PID values in both ready and exit must also be positive; integer CSV values must be canonical base-10 strings without whitespace, signs on positive values, or leading zeroes. Real-valued measurements use separate finite-number checks. The four sparse state records must be present at frames 151, 301, 451, and 601; counts must be nonnegative integers, health and position sums finite, and every sample must explicitly report `camera=combat`.

Only successful S_OK Present completions with valid monotonic QPC ticks contribute to FPS. The analyzer uses the exact measurement interval, reports per-run and per-replicate descriptive FPS, standard deviation and completion-gap tails, and applies the existing edge, stall, failed-Present, dropped/invalid-clock/export, and pending-export checks. Window observations must cover the measurement edges and show a visible, non-iconic game window. Each recorded observation must last at most 250 ms, and intervals must be ordered, nonoverlapping, and have distinct increasing start ticks. At least two observations must overlap the measurement phase. Start-to-start cadence and measurement-edge gaps retain the existing 1.5-second maximum. A single phase-spanning observation, overlapping/duplicated records, or stalled window reads cannot substitute for repeated samples. These checks bound sampled evidence; they do not establish continuous visibility or foreground state between samples. Older captures violating these bounds are incompatible and must not be repaired by rewriting observations.

A run with mixed foreground/background observations can be analyzed individually, but it cannot qualify for comparison. Every comparison run must be uniformly foreground or uniformly background, and all runs must use the same mode. Comparison paths are canonical Windows paths, unique case-insensitively within and across groups. Duplicate baseline paths, duplicate candidate paths, or any baseline/candidate overlap reject comparison. Existing Present-owner/QPC duplicate checks remain in force.

Replicates must match the existing evidence contract, including telemetry mode, a valid matching controller SHA-256 on every compared run, source and test Options.ini hashes, requested settings, declared and captured affinity, launcher configuration, resolution, swap interval, seed, map, camera, roster, and exact measured fixture-state samples. For every run, the analyzer resolves the receipt's launcher configuration path and verifies it is that runtime's actual `launcher.lcf`, then checks its raw SHA-256 and parsed command against the receipt. The absolute path remains in per-run provenance; comparisons match the verified configuration's SHA-256, command content, and any other semantic fields while excluding only the run-specific path. Each replicate group must have a consistent source snapshot and executable identity. The parser validates executable bytes against controller receipts, but it does not reconcile source commit/snapshot claims with a root build manifest.

## Named R2 profile contract table

The default remains the original 512-unit fixture and emits its original marker shape. The process reads `RTS_RENDERED_BATTLE_PROFILE` only when `-runRenderedBattleBenchmark` is present. Leave the variable unset to select the legacy case. The six exact values below select R2 profiles; every other value is rejected for a benchmark launch and ignored for ordinary/menu startup. The profile marker uses schema `ggc.r2.rendered-battle-profile.v1`, and every explicit profile repeats its profile and phase identity in its roster and phase markers. The shared phase contract is `ggc.r2.rendered-battle.phase.normal30hz-150-450-1080p.v1`.

Named R2 profiles have a bounded 180-second fixture wall budget so slower machines can complete all 600 simulation advances at maximum graphics. The 150 warm-up and 450 measured advances, 30 Hz logic target, uncapped rendering, and acceptance requirements remain unchanged. The legacy default benchmark retains its 45-second budget; visual capture and the ordinary diagnostic retain their 120-second budgets. A wall-limit exit is still an incomplete measurement and must never be counted as acceptance.

Template indices are fixed per faction: `0=tank`, `1=vehicle`, `2=infantry-A`, `3=infantry-B`. Slots retain the America, China, GLA, America sequence repeated; slots 0–3 are team 0 and slots 4–7 are team 1. Per-slot `templates=` markers name all four faction-specific templates and their exact counts, including zeroes. `unit_type_sequence=` records the ordered type index for each created unit, so order is part of the frozen roster identity.

| Profile ID | Total units | Per-slot counts `0,1,2,3` | Ordered unit-type sequence per slot | Roster contract |
|---|---:|---|---|---|
| `combined_arms_256` | 256 | `4,4,12,12` | `0×4, 1×4, 2×12, 3×12` | `ggc.r2.rendered-battle.roster.combined-arms-256.v1` |
| `combined_arms_512` | 512 | `8,8,24,24` | `0123` repeated 8 times, then `23` repeated 16 times (legacy creation order) | `ggc.r2.rendered-battle.roster.combined-arms-512.v1` |
| `mechanized_256` | 256 | `16,16,0,0` | `0×16, 1×16` | `ggc.r2.rendered-battle.roster.mechanized-256.v1` |
| `mechanized_512` | 512 | `32,32,0,0` | `0×32, 1×32` | `ggc.r2.rendered-battle.roster.mechanized-512.v1` |
| `infantry_line_256` | 256 | `0,0,16,16` | `2×16, 3×16` | `ggc.r2.rendered-battle.roster.infantry-line-256.v1` |
| `infantry_line_512` | 512 | `0,0,32,32` | `2×32, 3×32` | `ggc.r2.rendered-battle.roster.infantry-line-512.v1` |

The faction-specific templates are America: `AmericaTankCrusader`, `AmericaVehicleHumvee`, `AmericaInfantryRanger`, `AmericaInfantryMissileDefender`; China: `ChinaTankBattleMaster`, `ChinaTankGattling`, `ChinaInfantryRedguard`, `ChinaInfantryTankHunter`; and GLA: `GLATankScorpion`, `GLAVehicleTechnical`, `GLAInfantryRebel`, `GLAInfantryTunnelDefender`. The analyzer rejects unknown, incomplete, contradictory, or mismatched profile, roster, density, sequence, and phase identities. Replicate comparison requires the same complete profile contract across every run; the explicitly named `combined_arms_512` case cannot be mixed with the legacy default, even though their unit mix is the same.

When the R2 candidate defines `RTS_RENDERER_RIGID_INSTANCING_METRICS`, an explicitly named profile appends two optional snapshots to the existing `warmup_begin` and `measurement_stop` phase records. Each snapshot carries schema `ggc.r2.rendered-battle-rigid-draw-metrics.v1`, its matching logic frame, the API status, and seven cumulative native renderer counters. The analyzer accepts only a complete pair with exact fields and matching phase frames. Its `warmup_plus_measurement_delta` spans from the `warmup_begin` snapshot through `measurement_stop` (the full 150-frame warm-up plus 450 measured frames, 600 logic-frame advances). `counter_delta_scope` publishes both snapshot frame numbers and that full-span scope; this is not a measured-only delta or the Present/FPS interval.

These are renderer admission and route-attempt counters, not proof of GPU execution or completion. `captured_draws` counts draws accepted into a pending rigid batch; `instanced_batches` and `instanced_instances` count instanced calls that returned success; `singleton_ordinary` counts single-item batches sent through the ordinary route; `unsupported_fallbacks` counts instanced calls that returned unsupported; `ordinary_fallback_draws` counts ordinary fallback submissions attempted for those multi-item batches; and `rejected_draws` counts enabled capture requests rejected by eligibility checks. Even a successful instanced API return records route admission, not GPU completion. The analyzer exposes these values only under `render_admission_metrics`, separately from workload identity, FPS qualification, and GPU completion evidence. R1 control captures without this compile-time capability remain valid without the optional fields. The legacy default keeps its original marker shape; metrics add no per-frame polling or separate report records.

## Shadow multipage capture

Future captures must publish `ggc.shadow-upload-experiment.v2` in both ready and exit receipts. It retains every v1 field and adds `multipage_arena`, exactly `default` or `disabled`, and `RTS_SHADOW_MULTIPAGE_ARENA` to the exact `environment_values` object. The four required environment entries are `RTS_SHADOW_UPLOAD_REUSE`, `RTS_SHADOW_UPLOAD_ARENA`, `RTS_SHADOW_STREAM_REUSE_DIAGNOSTICS_DIR`, and `RTS_SHADOW_MULTIPAGE_ARENA`. The multipage entry must be JSON null for `default` (capture an absent variable) or string `"0"` for `disabled`. Missing, extra, or mismatched entries reject the receipt. Duplicate JSON keys also reject receipts. Ready and exit must agree exactly. The candidate source interprets exactly `0` as one page and uses four pages by default; this analyzer records the request rather than measuring effective page count or proving that a particular binary implements that behavior.

Original v1 receipts omit multipage capture. Individual analysis retains `identity.shadow_multipage_arena: "unknown"` without silently assuming a default. Every comparison requires a known, matching `default` or `disabled` request across all runs, even when all omitted values would otherwise match. No source hash or unsupported-build exemption substitutes for captured evidence.

An existing v1 run may optionally supply its original `ggc.shadow-multipage-environment-proof.v1` file without changing ready/exit receipts. Use an explicit path; the analyzer never discovers or creates proofs automatically:

```powershell
python tools/rendering-benchmark/analyze_r1.py analyze RUN_DIRECTORY --multipage-proof ORIGINAL_PROOF
python tools/rendering-benchmark/analyze_r1.py compare --baseline BASELINE_A BASELINE_B --candidate CANDIDATE_A CANDIDATE_B --multipage-proof BASELINE_A PROOF_A --multipage-proof BASELINE_B PROOF_B --multipage-proof CANDIDATE_A PROOF_C --multipage-proof CANDIDATE_B PROOF_D
```

The proof must bind the canonical absolute run path, fresh shell PID to the launcher's recorded parent PID, controller SHA-256, expected executable SHA-256, and source snapshot SHA-256. It must identify `RTS_SHADOW_MULTIPAGE_ARENA`, declare `effective_request: "default"`, set `verified_process_environment_absent` exactly true, and provide a nonnegative JSON integer `inherited_entries_removed`. Its timezone-aware ISO `created_utc` must strictly precede the launcher's `started_utc` and be no later than ready's `created_utc` when present. Timestamps preserve up to seven fractional digits. Missing/malformed fields, invalid bindings, duplicate keys, unreadable proofs, or inconsistent timestamps reject supplied evidence. An analyze command accepts at most one proof option; repeated options reject before run analysis, even when they name the same proof. Compare proof bindings must name a listed run exactly once. The original proof schema supports only absent/default requests and only v1 receipts; it cannot certify a disabled request or replace v2 capture.

Output preserves the original proof path and raw SHA-256 in `identity.shadow_multipage_evidence`. Comparison matches the normalized request, allowing v1 plus a valid original proof to compare with v2 default capture when all other semantic settings match. Proof provenance remains in each run's output. Proofs are operator evidence, not cryptographic authentication of their author or an independent observation of the game's inherited environment. Preserve the immutable original proof and its capture provenance; a retrospective assertion cannot establish that it existed before launch. The parser checks recorded time and identity consistency, and does not independently authenticate creation time, source/build capability, actual page count, or unchanged environment between parent observation and game start.

Legacy per-run analysis may retain a missing controller hash in minimalPresent/detailed mode, but comparison rejects every missing or malformed controller hash, including groups where all hashes are absent. Hash comparison is case-insensitive. When ready/exit supply an optional `controller_script_path`, they must agree on that absolute path, and the parser verifies the regular, nonsymlink controller artifact bytes against `controller_script_sha256`; missing or changed artifacts reject. The path is retained as run provenance, while comparisons match the verified hash rather than run-specific paths. Without that path, the controller hash remains a recorded identity claim; it does not independently prove which controller artifact executed. Preserve new capture provenance rather than adding unsupported legacy exceptions.

## Operator exclusion marker

A `qualification-exclusion.json` file at a run's root is a hard exclusion. A valid marker is a JSON object with schema `ggc.performance-exclusion.v1`, `excluded` exactly `true`, and a nonempty string `reason`. Duplicate JSON keys are invalid. For a valid marker, the analyzer preserves the reason in its rejection. An unreadable or malformed marker, wrong schema, false or invalid `excluded` value, or missing/invalid reason also rejects the run; a present invalid marker is never treated as absent. Per-run analysis rejects it, and a comparison containing that run has `data_comparable: false`.

## Graphics-quality limits

Visual inspection runs are ineligible for numerical analysis. The opt-in test-support mode `RTS_RENDERED_BATTLE_VISUAL_CAPTURE=1` emits `RENDERED_BATTLE_VISUAL_CAPTURE_ONLY numerical_eligible=0 wall_cap_ms=120000` into the native diagnostic and extends its wall cap to 120,000 ms. The analyzer rejects any diagnostic containing `RENDERED_BATTLE_VISUAL_CAPTURE_ONLY`, irrespective of marker fields, position, or completed measurement phases, before opening Present or GPU timing CSV files. Comparison returns a rejection without numerical summaries for such a run. Keep visual evidence separate from numerical benchmark evidence.

The separate opt-in `RTS_RENDERED_BATTLE_BACKGROUND_STARTUP=1` support mode leaves the default 150-frame warmup and 450-frame measurement contract unchanged. The analyzer has no source snapshot or executable hash allowlist that blocks a control and candidate built with the same support patch. Each run must still satisfy all captured identity, workload, window, and original parent environment proof checks, and each replicate group must retain one consistent build identity. Changed binaries or snapshots require matching newly captured evidence; old proofs cannot certify them. This parser does not independently verify the startup support mode or bind a binary to a source/build manifest.

The `ready.json` settings are controller-declared requests, including 8x MSAA and 16x anisotropic filtering. In `minimalPresent` mode, the Present CSV provides observed dimensions such as 1920x1080, but effective adapter and MSAA state are not measured; effective anisotropic filtering is not measured by this analyzer. A minimalPresent comparison therefore establishes only descriptive timing-data comparability under matched requested settings and observed Present dimensions.

In `presentGpu` mode, the analyzer requires the published GPU CSV, reconciles its footer, joins GPU rows to Present rows, and checks sampled effective dimensions, MSAA, resolve state, and adapter identity. This is bounded sampled evidence. It is not full-phase proof of graphics quality or an FPS acceptance decision. The analyzer does not measure CPU phase cost, display scanout, physical window geometry, visual correctness, or statistical significance.

## Comparison output meaning

Comparison JSON exposes `data_comparable`. The legacy `accepted` field remains as a deprecated alias with the same value. Every comparison sets `stage_accepted` to `false` and `stage_status` to `not_evaluated`; this analyzer does not implement the separate stage gate. A zero exit status from `compare` means only that evidence passed the data-comparability checks; a zero exit status from `analyze` means the run is qualified under run-level analyzer checks. Neither result establishes stage acceptance. The reported FPS delta, replicate standard deviation, and completion-gap tails are descriptive statistics; comparability alone never establishes an FPS gain.

## Capture provenance and portability

The parser tests and package layout are portable, but captured runs retain their original Windows absolute-path provenance. Receipts refer to exact game and launcher binaries at their captured paths, and analysis verifies current files against recorded hashes and settings such as the profile's Options.ini. Preserve each executable as an immutable binary with its original absolute path and SHA-256. A receipt folder alone is insufficient for replaying analysis elsewhere; do not rewrite receipt paths to make a run appear portable. This analyzer does not bind captured binaries to a source commit or build manifest. The controller, game, window helper, and captured evidence producers are not included in this package.
